# Grouping With Packages

## Key Concepts

It can be useful, particularly in larger systems, to have distinct logical
groupings of classes[^fun]. These groups of classes are called **packages**.

The classes within a package all 'fit together' in some sense; typically,
they are used together to implement a particular feature of the system, or
they form a distinct architectural component of the system.

For example, you might have an application with one group of classes that
are used to provide a user interface, and another group of classes that
handle interaction with a database. You could put the first group of classes
in a package named `myapp.ui` and the second group in a package named
`myapp.database`.

Or you might organize things functionally, putting all the classes that
relate to placing an order for a product in the `myapp.orders` package, and
all the classes that relate to delivering the ordered product in the
`myapp.delivery` package.

A package constitutes a **namespace** for your code. Within that namespace,
class names need to be unique, but the same constraint doesn't apply across
namespaces.

This can be useful in large projects, where different teams are working on
different parts of a system. It may well happen that two teams choose to use
the same class name for different purposes. This would cause problems if all
the code were part of a single namespace, but if the teams put their classes
in differently-named packages then the problem disappears.

### An Example From Java

The Java language ships with a huge standard library comprising thousands of
classes. These are organized into a large number of packages.

The package `java.util` contains [a class named `Date`][date1], which
represents a date & time with millisecond precision. Another package,
`java.sql`, contains a different class that is [also named `Date`][date2],
representing a date retrieved from an SQL database.

These two classes are allowed to have the same name because they reside
in differently-named packages. If you ever needed to reference both classes
from within the same file of source code, you could use the package names
to distinguish between the two.

## Packages in Kotlin

### Putting Code in a Package

This is fairly straightforward. If you put a **package declaration** at the
top of a `.kt` file, all of the classes and functions defined within that
file will become part of the package that you have named in the declaration.

For example, to put class `Customer` in the package `myapp.orders`, you
would write

```kotlin
package myapp.orders

class Customer(val name: String, val email: String)
```

### Package Naming Conventions

Package names generally have two or more elements, separated from each other
by a period. Each element should use lowercase letters if possible, although
a lower camel case naming style is permitted. Underscores should not be used.

In code intended for public release, it is advisable to make package names
unique by incorporating a reversed domain name as a prefix.

Consider, for example, the Kotest libraries that you have already used for
unit testing. The website for Kotest is hosted at the domain `kotest.io`, and
all of the code in the libraries is organized into packages whose names
begin with `io.kotest`.

### Implications of Packaging

Organizing functions and classes into packages affects how we use those
functions and classes. For example, if a function is defined in one package
and the code calling that function belongs to a different package, we will
need to either use an `import` statement to access the function, or use
its **fully-qualified name** (FQN).

Use of packages also affects where the output from the Kotlin compiler is
stored. Files of bytecode are organized into a directory hierarchy that
mirrors the package names declared in the corresponding files of source code.

Typically, we organize source code in the same directory hierarchy as that
generated by the compiler. Thus, if a class is defined to be in the package
`myapp.orders`, we would normally locate its source file in a subdirectory
`myapp/orders` of the top-level source directory. This isn't required for
code to compile, but it is considered to be good style.

## Task 14.1

Open `tasks/task14_1` in your preferred code editing environment. This is a
KT project containing a `Customer` class and a small demo program that uses
the class. Examine the class definition and program now.

Currently, neither the class nor the program have an explicit package
declaration, so both will be treated as if they are part of an unnamed
'default package'.

Build the application with

    ./kotlin build

The code should compile without any problems.

Then examine the contents of the JAR file in `build/tasks/_task14_1_jarJvm`.
You can do this from the command line using[^jar]

    jar -tf task14_1-jvm.jar

The output displayed in the terminal should include the following lines:

    Customer.class
    MainKt.class

### Using a Package

Edit `Customer.kt` and add this line to the start of the file:

```kotlin
package myapp.orders
```

Try building the application again. You should get a compiler error, because
`Customer` and `main()` are no longer in the same package.

Edit `Main.kt` and try fixing the issue by using the FQN of the class:

```kotlin
fun main() {
    val customer = myapp.orders.Customer("Joe", "joe@example.com")
    println(customer)
}
```

Verify that the application now compiles successfully.

Next, try using an import statement for `Customer` instead of its FQN:

```kotlin
import myapp.orders.Customer

fun main() {
    val customer = Customer("Joe", "joe@example.com")
    println(customer)
}
```

Once again, verify that the application compiles successfully.

Use the `jar` tool again to examine the contents of the JAR file containing
the application bytecode. You should now see these lines:

    myapp/orders/Customer.class
    MainKt.class

Finally create a subdirectory path under `src` named `myapp/orders`. Move
`Customer.kt` there but leave `Main.kt` in `src`. This ensures a directory
structure for source code that mirrors the directory structure generated
by the compiler for bytecode, which is considered good practice.

Verify that the application still compiles after this change.

## Packages in COMP2850

You may have noticed that packages generally haven't been used in the tasks
and code samples that we've provided for you.

This has been done to keep things simple, and because the amount of code used
in a task is generally very small, so there is not much benefit to be gained
by putting functions and classes into packages.

**In larger pieces of work, such as your Semester 2 team project, we will
expect you to make sensible use of packages to keep all of your code
well organized.**

to functions.
