# The Kotlin Toolchain

In this section, we dig a little deeper into what you can do with the Kotlin
Toolchain.

(For convenience, we will refer to it from this point onwards as **KT**.)

## Dependencies

KT allows you to specify the external libraries on which an application
depends. It will download these dependencies and then cache them locally for
use by the application.

Let's see how this works in practice. Open the directory `tasks/task1_3_1`
in your repository using your preferred code editing environment. This
contains a fancier version of the "Hello World" program from earlier.

You should see a file named `libs.versions.toml`. This is the top-level
**library catalog** for the project. Library catalogs are a standard way of
capturing details of the external libraries used by an application.

```{code} toml
:filename: libs.versions.toml
:linenos:
[versions]
datetime = "0.8.0"
mordant = "3.0.2"

[libraries]
datetime-jvm = { module = "org.jetbrains.kotlinx:kotlinx-datetime-jvm", version.ref = "datetime" }
mordant = { module = "com.github.ajalt.mordant:mordant", version.ref = "mordant" }
```

This catalog has two sections. The `libraries` section (lines 5&ndash;7) lists
two libraries, referring to them by the keys `datetime-jvm` and `mordant`.
Note that you get to choose these keys yourself. It is normal to use a
shortened version of the library name here.

Each key is associated with a **module identifier** and **version reference**.
The module identifier specifies the external library we wish to use by its
[**Maven coordinates**][mav]. Maven coordinates are a standard way of uniquely
identifying a software library in the JVM ecosystem.

The `versions` section (lines 1&ndash;3) links the version references from the
`libraries` section with specific library version numbers. This separation
between library identifiers and version numbers is done to simplify
maintenance, because changes to library versions are likely to be made much
more frequently than changes to the set of chosen libraries[^ver].

The `module.yaml` file looks like this:

```{code} yaml
:filename: module.yaml
:linenos:
product: jvm/app

dependencies:
  - $libs.datetime.jvm
  - $libs.mordant
```

Line 1 is the same as before. Lines 3&ndash;5 introduce a `dependencies`
section, containing a list of library references. The `$libs.` prefix tells
KT that it needs to look in the library catalog for further details. After
this prefix we specify a key from the catalog, but with each hyphen character
changed to a period. Thus `$libs.datetime.jvm` refers to the key
`datetime-jvm` in the catalog[^fmt].

Now examine the two source code files in `src`. The file `Date.kt` defines a
function that uses the `kotlinx-datetime` library to determine today's date.
The file `Main.kt` contains a program that uses the `mordant` library to
display a "Hello World" message and the date in a colourful way. Notice how
these files reference library features using `import` statements.

Finally, enter `kotlin run` and watch the terminal window closely. You should
see some indication that KT is resolving dependencies (i.e., downloading
them and caching them locally). Once this is completed, the application will
be compiled and executed.

On any given system, dependencies need to be resolved only once, so subsequent
uses of the `build` or `run` commands will be faster.

## Configuring Kotlin & JDK Versions

If you wish to use a specific version of Kotlin, add something like the
following to the `settings` section of `module.yaml`:

```yaml
settings:
  kotlin:
    version: 2.4
```

If you wish to configure a specific version of the JDK, you can use this:

```yaml
settings:
  jvm:
    jdk:
      version: 25
```

:::{note}
If you want to make KT use an already-installed version of the JDK instead
of provisioning a version for itself, you will need to use the `version`
setting shown above, specifying the major version number of the
already-installed JDK.

You will _also_ need to make sure that the `JAVA_HOME` environment variable
is defined, and that it references the directory where that JDK has been
installed.
:::

## Main Class Configuration

When the JVM is the target, files of Kotlin source code are transformed into
**class files** containing Java bytecode. When KT runs your application, it
assumes by default that one of these class files is named `MainKt.class`,
and that this contains the bytecode for the `main()` function. This is
guaranteed to be the case if your `main()` function is in a file named
`Main.kt` or `main.kt`, in the `src` directory.

You are free to put `main()` in a source file with a different name if you
wish, but in that case you will need to tell KT where to find `main()` in all
of the bytecode generated by the compiler.

For example, suppose that you put the "Hello World" program's `main()` in a
file named `Hello.kt`. In such a case, the compiler will put the bytecode of
`main()` in a file named `HelloKt.class`, and you will need to add the
following to `module.yaml`:

```yaml
settings:
  jvm:
    mainClass: HelloKt
```

Notice that the name of the _class file_ is specified here, minus its `.class`
extension, not the name of the Kotlin source file.

You will also need to configure the main class explicitly if the source file
containing `main()` has been made part of a **package**. For example,
suppose your "Hello World" program is in a file `Main.kt` that looks like
this:

```{code} kotlin
:filename: Main.kt
package comp2850.hello

fun main() {
    println("Hello World!")
}
```

Here `main()` is declared to be part of the package `comp2850.hello`. Thus
you will need the following configuration in `module.yaml`:

```yaml
settings:
  jvm:
    mainClass: comp2850.hello.MainKt
```

## Deployment

We've seen already that KT's `build` command compiles your application into
a single JAR file. This file can be run by KT, but it isn't totally portable,
as it doesn't include any dependencies. Even a very simple application is
going to depend, at minimum, on Kotlin's [standard library][lib].

To deploy an application on systems that don't have KT installed, you will
need to include the application's dependencies. You can do this using KT's
`package` command.

Try this out now. In a terminal window, `cd` to the `tasks/task1_3_1`
directory of your repository. Then enter

    kotlin package

You will see that there are now _two_ subdirectories of `build/tasks`, named
`_task1_3_1_jarJvm` and `_task1_3_1_executableJarJvm`. Each contains a
JAR file.

Compare the sizes of these two JAR files (e.g., using `ls -l` on Linux or
macOS). You should find that the 'executable JAR' is considerably larger than
the other, because it includes the Kotlin standard library and the two other
library dependencies (`kotlinx-datetime` and `mordant`). This larger file
can be deployed on any system that has a JVM installed.

To test this out, try executing the application directly on the JVM, like so:

    java -jar task1_3_1-jvm-executable.jar

This will not work if you try it with the other JAR file.

:::{note}
If you are curious about what is actually inside these JAR files, you
can examine their contents in the terminal window, using the `jar` tool:

    jar -tvf task1_3_1-jvm-executable.jar

Alternatively, you can use `unzip -l` (since JAR files are really just
Zip archives in disguise).
:::

## Project Initialization

KT can initialize a Kotlin project for you, using the `init` command.

Try this out now. In a terminal window, `cd` into the `tasks/task1_3_2`
directory of your repository. This currently contains a README file and
nothing else.

Input the command

    kotlin init

A menu of options will appear. Use the arrow keys to select the option
"JVM Console Application", then press {kbd}`Enter`

If you list the contents of `task1_3_2`, you will see that the following
have been added:

- A shell script named `kotlin`
- A Windows batch file named `kotlin.bat`
- A `module.yaml` file, declarating this to be a JVM-based application
- A `src` subdirectory, containing some source code files
- A `test` subdirectory, containing some unit tests (discussed later)

The script and batch file can be used to invoke KT. For example, you can do

    ./kotlin run

to run the application on a Linux or macOS system, instead of using the
globally-installed `kotlin` command.

:::{note}
Including the script and batch file makes the project easier to share
with other people.

These people will not need to install KT or even the JDK themselves in order
to build and run the application, as the script and batch file will do that
for them.

IntelliJ IDEA can automatically add the script and batch file if they are not
present in a KT project. For convenience, we have included them in the files
we have provided for most of the tasks in this guide.
:::
